# Six-scenario performance evidence

Status: dated historical evidence, 2026-09-13. Measurements and necessary evidence verification are complete. This records controlled experiments and candidate changes, not a current execution contract, a per-task checklist, or a requirement to use a Skill. Both supplemental scenario-6 arms used GPT-6 Astra / ultra with existing context; managed took longer at business completion, evidence completion and report completion. The universal six-case speed objective was not achieved.

The fresh xhigh managed Agent completed four existing-container tasks in **195.375 seconds**, compared with **234.776 seconds** for the direct Agent sample, an observed reduction of **39.401 seconds, or 16.8%**. The additional context-exposed ultra scenario-6 sample went the other way: managed business completion took **583.953675 seconds**, versus **511.061550 seconds** for direct, and managed was also slower through evidence and report completion. Neither result is a statistical guarantee. The first successful managed case-1/3 trial took **249.276 seconds**, longer than direct, and the next trial failed before business execution; both remain recorded. **The universal six-case performance target is not proven.** The earlier managed **110.849-second** case and direct **90.322-second** interval had different preparation preconditions and remain separate observations.

## Scope and measurement

The six cases exercise fixed component versions. Necessary source preparation, environment configuration, incremental compilation, business validation, process exit and resource release belong to the measured task. Component updates and client installation performed outside the experiment do not.

The original direct Agent was assigned GPT-6 with xhigh reasoning, ordinary native tools and SSH, without Skills or VAWS management tools. The original managed Agent used the same requested model/reasoning class and supported TaskClient interfaces without Skills. Each independently chose its steps from the task brief and public entry documentation; the final managed case-1/3 Agent did not read earlier drivers, reports or performance implementation. The experiment owner supplied the fixed candidates and hardware scope. The additional scenario-6 comparison is separately labelled GPT-6 Astra / ultra with existing context in both arms; it does not replace those original xhigh observations.

| Metric | Boundary |
| --- | --- |
| Agent completion | First actual tool action to the last observed business exit/resource release. Exploration, local scripts, failed attempts, recovery and intervening work remain included. |
| Evidence completion | First actual tool action through necessary preservation checks and evidence retrieval/verification. Report writing is a later, separate boundary. |
| Direct successful SSH | One successful local SSH command, including connection, remote script, Python exit and SSH return. Earlier discovery, provisioning and compilation are separate. |
| Managed task | Submission to observed terminal state and resource release through the owner. This is not the full autonomous Agent duration. |
| Business | Imports, initialization and assertions measured inside the business process. It is not isolated kernel latency and does not include the whole interpreter shutdown. |
| Stage | A monotonic operation span or adjacent progress observations on the same clock. Progress intervals can include polling and transitions. |

Local and remote wall clocks differ. Durations use their own clock; no result subtracts a remote timestamp from a local timestamp. Overlapping SSH and compilation durations are not added to manufacture an Agent total. Dispatch and report completion are separate endpoints.

The fixed business source baselines were vllm `e7739c8720974cdd442c0f051cc08a41a4e799c2` and vllm-ascend `88398f3c885d1264cde65069dc8a3e9adf6487f0`, with Python 3.12.13, torch 2.10.0+cpu, torch_npu 2.10.0.post4.dev20260715 and CANN 9.1.0. Source edits produced separate fixed snapshots without updating these components.

Other bounded evidence: a single explicitly selected device-existence query took **0.561 s**; strict, multi-device and unknown conditions retained the broader path. Earlier owner spans measured admission **2.454 s**, activation **1.368 s** and release **1.447 s**; a later incremental sample measured **0.900 / 0.809 / 1.376 s**. They are different samples, not a controlled per-change speedup claim.

One concrete preparation bottleneck was repeated environment activation, rather than virtual-environment creation itself. In the old **15.034 s** preparation script, sourcing ATB took **14.569 s**, while the actual venv step took only **0.053 s**. ATB's automatic ABI detection imports torch in two separate Python processes. The owner now passes an already verified ABI when available and retains automatic detection when it is unknown. A measured activation preamble then took **0.428 s**. The separate lightweight preparation measured **0.126 s** for venv creation and **0.097 s** for dependency metadata, without importing torch. These are bounded phase measurements, not a claim that an entire managed run takes less than a second.

The final cold-container repeat took **90.646792 s** including required container preparation, with a locally observed materialize-to-marker interval of **8.855827 s** and business **7.472508 s**. The earlier **224.058 s** cold run had a **97.442 s** interval covering carrier preparation, serial Git pushes and control/transport. This supports recording less repeated work in the later path, but does not isolate the entire end-to-end difference as a Git-only benefit.

A 1,103-file completed proof compressed from **301,483 B to 77,849 B**, with approximately **5.2 ms** local encoding and **2.6 ms** decoding and exact dictionary recovery. Hard size, complete-stream and digest checks remain. This measures size and local CPU cost, not remote throughput. The earlier restore took **2.448 s** remotely and emitted **191,269 B**; its **9.535 s** gap before the next preparation step included log draining and control transitions, not just transfer.

The retained slow unchanged-source probe took **63.778 s**. Its observed verify-profile to launch-pending interval was **29.868 s**, and initial preparing to prepare-root was **10.479 s**. No independent RPC measurements identify the causes of these intervals. A later probe took **25.547 s**; neither the slow sample nor its uncertainty should be removed.

Case 6b spent **40.615977 s** between its first preparing observation and prepare-root. Its historical container-check/fallback phases were not retained, and a full local test suite ran concurrently. Subsequent read-only matches cannot reconstruct that earlier outcome, exclude a fallback or attribute the interval to CPU contention. Precise before/after timing claims from this sample would be unsupported.

The new observation phases preserve match/fallback reasons and elapsed time. In case 6c, the actual preparation log records an existing-container **match in 4.999891 s**, followed by SSH-port reservation **0.944076 s**, with no container-bootstrap phase. The locally observed incremental step to marker writing was **49.962558 s**, and verify-profile to allocation was **16.580900 s**. These intervals include operation and observation overhead; they are not pure compiler or verification CPU timers. Run c's complete submission-to-release time was **110.848804 s**, with business correctness, actual candidate-kernel use and quiet release confirmed. Its separately measured container setup was **36.557268 s**, establishing the existing-container precondition before the case began.

Remaining native costs are only partly attributed. The three OPC processes in case 6c already ran in parallel; their same-remote-clock runtime-start to cleanup envelope was about **34.84 s**. Ninja printed variants as they completed, not as proof of serial execution. The build log still shows recompilation of `runtime_kb_api.cpp` and linking of `liboptiling.so` and `libcust_opmaster_rt2.0.so`. Measuring unchanged host-build dependencies is a candidate next investigation; byte-identical output from an equivalent source edit does not remove the requirement to compile that edit.

An existing read-only review bounded verify-profile start to its owned job becoming quiet at about **14.52 s**, followed by about **2.08 s** through allocation, including shared storage and binding. Activation, imports and hashes within the first interval were not separately timed; it cannot all be labelled import time. Code review identified potentially repeated capture/verify and source/copy/destination hash passes over the 1,103-file proof. Combining same-job proof with destination validation during copying is a possible future change, not a measured benefit, and would need to preserve mutation detection and atomic publication.

Running-to-release intervals of roughly 12–14 seconds include the complete Python process and result observation. The business timer of roughly 7 seconds does not include all interpreter shutdown. They must not be labelled entirely as management overhead.
